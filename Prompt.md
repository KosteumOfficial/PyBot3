PYBOT3: УНІВЕРСАЛЬНА PYTHON-БІБЛІОТЕКА ДЛЯ БОТІВ

1. Твоя роль

Ти досвідчений Python-розробник, архітектор бібліотек і open-source проєктів.

Твоє завдання: розробити повноцінну Python-бібліотеку PyBot3, призначену для створення ботів у різних месенджерах, соціальних мережах та інших платформах, які надають відповідні API для автоматизації.

PyBot3 має стати універсальним інструментом, який об'єднує можливості різних бібліотек для створення ботів під єдиним, зрозумілим API.

Це має бути справжня бібліотека, готова до встановлення через pip, використання в реальних проєктах, тестування та подальшого розвитку.

Не створюй лише демонстраційний приклад. Розроби реальну архітектуру та реалізуй її.

2. Головна концепція

Назва: PyBot3.

Призначення: універсальна бібліотека для створення ботів на Python.

Основна ідея: розробник пише бізнес-логіку один раз, а бібліотека надає спільний інтерфейс для підтримуваних платформ.

Наприклад, розробник повинен мати змогу створити команду "/start", яка працює в Telegram і Discord, використовуючи спільну логіку обробки.

Водночас враховуй, що різні платформи мають різні можливості, правила, API та обмеження. Не симулюй функції, яких платформа не підтримує.

PyBot3 повинна бути:

- Легкою та швидкою.
- Зручною для новачків.
- Достатньо потужною для складних проєктів.
- Асинхронною за замовчуванням.
- Модульною та розширюваною.
- Документованою.
- Типізованою.
- Зручною для тестування.
- Незалежною від конкретного месенджера.
- Сумісною з актуальними стабільними версіями Python, які підтримують усі вибрані залежності.

Не перевантажуй бібліотеку непотрібними абстракціями.

3. Підтримувані платформи

Архітектура повинна дозволяти додавати нові платформи через окремі адаптери.

Передусім спроєктуй підтримку:

1. Telegram Bot API.
2. Discord API.
3. WhatsApp Business Platform API.
4. Інших платформ через систему адаптерів і розширень.

Не заявляй про підтримку платформи, доки її адаптер не реалізований і не протестований.

Для кожної платформи:

- Використовуй офіційні API.
- Дотримуйся правил і обмежень платформи.
- Не обходь авторизацію, ліміти або захисні механізми.
- Документуй необхідні токени, налаштування та дозволи.
- Вказуй, які функції доступні.
- Не використовуй неофіційні способи автоматизації, якщо вони порушують правила платформи.

Особливо врахуй, що WhatsApp Business Platform відрізняється від звичайного WhatsApp і може вимагати налаштування бізнес-акаунта, вебхуків та відповідних дозволів.

4. Простий API

API має бути максимально зрозумілим.

Бажаний приклад використання:

from pybot3 import Bot

bot = Bot(
    platform="telegram",
    token="YOUR_TELEGRAM_TOKEN"
)


@bot.command("start")
async def start(ctx):
    await ctx.reply("Привіт! Я працюю на PyBot3.")


@bot.command("help")
async def help_command(ctx):
    await ctx.reply("Чим можу допомогти?")


@bot.message()
async def handle_message(ctx):
    if ctx.text:
        await ctx.reply(f"Ти написав: {ctx.text}")


bot.run()

Це цільовий API, а не дозвіл залишати функції нереалізованими.

Перевір, щоб декоратори, контекст, маршрутизація, запуск та обробка помилок справді працювали.

Якщо API потребує змін, обери технічно обґрунтований варіант і поясни його в документації.

Передбач також можливість створювати ботів для декількох платформ у межах одного застосунку.

5. Архітектура адаптерів

Створи спільний інтерфейс адаптера платформи.

Кожен адаптер повинен відповідати за:

- Авторизацію.
- Підключення до API.
- Отримання подій.
- Перетворення подій на спільні об'єкти PyBot3.
- Відправлення повідомлень.
- Обробку помилок API.
- Повторні запити, коли це доречно.
- Коректне завершення роботи.
- Дотримання обмежень запитів.

Приблизна внутрішня структура:

PyBot3
├── Core
│   ├── Bot
│   ├── Router
│   ├── Dispatcher
│   ├── Context
│   └── Lifecycle
├── Adapters
│   ├── Telegram
│   ├── Discord
│   └── WhatsApp
├── Filters
├── Middleware
├── Handlers
├── Types
├── Exceptions
├── Utilities
└── Testing

Це логічна структура, а не обов'язкова структура назв папок.

Розділи спільну логіку та платформозалежний код.

Не створюй окрему реалізацію кожної функції для кожного месенджера, якщо її можна безпечно реалізувати в спільному ядрі.

Водночас не намагайся штучно об'єднати несумісні можливості різних платформ.

6. Система подій та обробників

Реалізуй підтримку таких подій:

- Нове повідомлення.
- Редагування повідомлення, якщо платформа це підтримує.
- Видалення повідомлення, якщо платформа повідомляє про таку подію.
- Натискання кнопок.
- Callback-події.
- Команди.
- Приєднання учасника.
- Вихід учасника.
- Події груп і серверів, якщо вони підтримуються платформою.
- Власні користувацькі події.

Приклад:

@bot.message()
async def on_message(ctx):
    print(ctx.text)


@bot.command("ping")
async def ping(ctx):
    await ctx.reply("Pong!")


@bot.event("member_join")
async def on_member_join(ctx):
    await ctx.reply("Новий учасник!")

Якщо конкретна подія не підтримується платформою, адаптер повинен чітко це позначати.

Передбач маршрутизатори, щоб розробники могли розділяти код за модулями.

Наприклад:

from pybot3 import Router

router = Router()


@router.command("profile")
async def profile(ctx):
    await ctx.reply("Твій профіль")


bot.include_router(router)

Підтримуй фільтри, пріоритети обробників і контроль того, чи повинні інші обробники продовжувати виконання після поточного.

7. Універсальний контекст

Створи об'єкт "Context", доступний кожному обробнику.

Він має надавати, де це можливо:

- "ctx.platform"
- "ctx.user"
- "ctx.chat"
- "ctx.text"
- "ctx.message"
- "ctx.command"
- "ctx.args"
- "ctx.reply()"
- "ctx.send()"
- "ctx.edit()"
- "ctx.delete()"

Передбач також доступ до оригінального об'єкта події конкретної платформи.

Наприклад:

native_event = ctx.native_event

Це необхідно для випадків, коли універсального API недостатньо.

Універсальні методи повинні мати узгоджену поведінку. Якщо певна операція недоступна на платформі, повертай зрозумілу помилку або використовуй задокументований результат.

Не приховуй несумісність платформ.

8. Повідомлення та вкладення

Реалізуй зручну систему роботи з повідомленнями.

Передбач підтримку:

- Тексту.
- Фото.
- Відео.
- Документів.
- Аудіо.
- Голосових повідомлень.
- Посилань.
- Кнопок.
- Вбудованих меню.
- Форматування тексту.
- Редагування та видалення повідомлень.

Можливості залежать від конкретної платформи.

Приклад:

await ctx.reply("Привіт!")

Надсилання фото:

await ctx.reply_photo("images/photo.png")

Кнопки:

from pybot3 import Button, Keyboard

keyboard = Keyboard(
    buttons=[
        [Button("Профіль", callback_data="profile")],
        [Button("Допомога", callback_data="help")]
    ]
)

await ctx.reply(
    "Обери дію:",
    keyboard=keyboard
)

Зроби об'єкти повідомлень, кнопок і клавіатур незалежними від конкретного адаптера.

Адаптер повинен перетворювати їх у формат відповідної платформи.

Не вдавай, що всі платформи мають однакові кнопки чи механізми callback.

9. Фільтри

Створи систему фільтрів.

Приклади:

@bot.message(filters.text)
async def text_handler(ctx):
    await ctx.reply("Це текстове повідомлення")

@bot.message(filters.command("start"))
async def start_handler(ctx):
    await ctx.reply("Привіт!")

Передбач фільтри для:

- Тексту.
- Фото.
- Відео.
- Документів.
- Користувачів.
- Чатів.
- Команд.
- Регулярних виразів.
- Власних умов.
- Комбінацій фільтрів через AND, OR та NOT.

Фільтри повинні бути швидкими, читабельними та зручними для розширення.

10. Middleware

Реалізуй middleware для обробки подій до та після виконання обробників.

Типові сценарії:

- Логування.
- Перевірка доступу.
- Вимірювання часу виконання.
- Обробка помилок.
- Завантаження даних користувача.
- Обмеження частоти викликів.
- Перевірка стану користувача.

Приклад цільового API:

@bot.middleware()
async def logging_middleware(ctx, call_next):
    print("Incoming event")

    result = await call_next()

    print("Event processed")
    return result

Документуй порядок виконання middleware та правила передавання результатів.

11. FSM та стани користувачів

Реалізуй FSM, тобто машину станів, для створення діалогів.

Наприклад, бот може послідовно запитувати ім'я, вік і країну користувача.

Не змушуй розробників самостійно реалізовувати весь механізм збереження станів.

Передбач:

- Створення станів.
- Перехід між станами.
- Отримання поточного стану.
- Очищення стану.
- Тимчасове збереження даних.
- Можливість підключення різних сховищ.

Для першої версії можна реалізувати сховище в пам'яті та SQLite.

Архітектура має дозволяти додати Redis у майбутньому.

Зазнач, що сховище в пам'яті не зберігає стани після перезапуску процесу.

12. Система плагінів

Реалізуй архітектуру розширень.

Плагін повинен мати можливість:

- Реєструвати команди.
- Додавати обробники.
- Реєструвати middleware.
- Додавати власні фільтри.
- Підключати сервіси.
- Реєструвати обробники життєвого циклу.

Приклад бажаного API:

from pybot3 import Plugin


class WelcomePlugin(Plugin):
    name = "welcome"

    def setup(self, bot):
        @bot.command("hello")
        async def hello(ctx):
            await ctx.reply("Вітаю!")

Плагіни повинні підключатися явно.

Не завантажуй випадковий код із мережі автоматично.

Документуй життєвий цикл плагінів, залежності між ними та правила реєстрації.

Використовуй перевірені залежності, якщо вони справді спрощують реалізацію.

Не додавай великі залежності лише заради однієї дрібної функції.

14. Помилки та надійність

Створи систему винятків.

Наприклад:

- "PyBot3Error"
- "AuthenticationError"
- "PlatformError"
- "RateLimitError"
- "NetworkError"
- "UnsupportedFeatureError"
- "HandlerError"

Назви можна змінити, якщо це покращить архітектуру.

Забезпеч:

- Зрозумілі повідомлення про помилки.
- Збереження оригінальної причини помилки.
- Обробку винятків у користувацьких обробниках.
- Контроль повторних запитів.
- Експоненційні затримки, коли вони доречні.
- Дотримання "Retry-After" та інших вимог API.
- Відсутність нескінченних циклів повторення.

Не повторюй запити автоматично, якщо це може призвести до дублювання небезпечних операцій.

20. Залежності

Використовуй мінімальну кількість залежностей.

Спочатку визнач, які компоненти необхідні для першої робочої версії.

Наприклад, можуть знадобитися:

- HTTP-клієнт.
- Інструменти для асинхронності.
- Бібліотека для роботи з конфігурацією.
- Інструменти тестування.

Для кожної платформи використовуй офіційний API та обґрунтований спосіб взаємодії з ним.

Якщо стороння бібліотека вже реалізує складну роботу з API, можна використати її як внутрішню залежність адаптера.

Однак зовнішній API PyBot3 повинен залишатися стабільним і зрозумілим.

Не встановлюй залежності, які не використовуються.

24. Правила якості

Обов'язково дотримуйся таких правил:

- Не залишай критично важливі функції у вигляді "pass", "TODO" або заглушок.
- Не підмінюй реальну реалізацію фіктивними відповідями.
- Не створюй зайвої архітектурної складності.
- Використовуй type hints.
- Дотримуйся PEP 8.
- Розділяй відповідальність між модулями.
- Не копіюй великі фрагменти коду між адаптерами.
- Не приховуй помилки через порожні "except".
- Не запускай небезпечні операції без необхідності.
- Не розкривай секрети в логах.
- Не заявляй про неперевірену сумісність.
- Не вигадуй API платформ.
- Перевіряй зовнішні API за актуальною офіційною документацією.

Якщо є вибір між красивим, але складним рішенням і простим, надійним рішенням, віддавай перевагу простому, якщо він задовольняє вимоги.

25. Результат

У результаті я хочу отримати реальну Python-бібліотеку PyBot3, яку можна:

- Встановити через pip після підготовки до публікації.
- Використовувати для створення ботів.
- Розширювати власними адаптерами.
- Тестувати без реальних API-токенів.
- Використовувати в невеликих і великих проєктах.
- Розвивати як open-source проєкт.

Починай з аналізу репозиторію, якщо він уже існує.

Якщо в репозиторії вже є код, спочатку перевір його, збережи працездатні компоненти та не перезаписуй проєкт без потреби.

Якщо репозиторій порожній, створи структуру з нуля.

Після кожного етапу:

1. Поясни, що реалізовано.
2. Переліч файли, які створено або змінено.
3. Запусти відповідні тести.
4. Покажи результати тестування.
5. Вкажи відомі обмеження.
6. Визнач наступний етап.

Не зупиняйся на написанні плану. Переходь до реальної реалізації та перевіряй результат.

Головний пріоритет: якісне універсальне ядро, простий API, надійність і можливість додавати нові платформи без переписування бібліотеки.
